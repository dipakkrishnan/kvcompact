# KV-cache compaction vs summary compaction: plan v2 (after Astra review)

## Hypothesis
When a session hits its context limit, a compactor that operates directly on the session model's KV cache
keeps more of what the rest of the session needs than a compactor that writes a summary, at an equal
memory budget.

## Fixed choices
- Subject (the session model): Qwen3-Coder-30B-A3B-Instruct, bf16, HF transformers (pinned version), 1x H200
  (61 GB of weights leaves too little workspace on an H100). 48 layers, 32 query heads / 4 KV heads (GQA), ~96 KiB/token.
- Artificial limit L = 32k tokens. The model's native window is much longer, so keeping original positions after pruning is safe.
- Budget B = 4k token-equivalents, counted in resident bytes (K/V plus indices plus masks), and
  identical across methods: same system prompt, same verbatim recent tail, same headroom.
- Selection is per GQA group (4 KV heads), so all methods share one granularity. No merging in v1.

## Methods (all produce a state of at most B)
1. full: no compaction (a reference, not a guaranteed upper bound)
2. recent: tail only
3. summary+tail: the compactor writes a summary, then the verbatim recent tail (the strong practical baseline)
4. snapkv: the real SnapKV algorithm (observation window plus pooling), with the original positions kept
5. tuned-heuristic: a search over SnapKV/H2O settings with the same compute budget as the kv-agent (separates "search" from "reasoning")
6. kv-agent: a frontier compactor (Claude) with a Python kernel over the subject's cache, recorded queries,
   token text and turn boundaries; selection-only edits; a defined probe budget (N probe generations,
   each capped at M tokens); development questions WITH answers from the prefix (so feedback is real, not self-graded)
7. ablation: the same kv-agent loop with Qwen itself as the compactor (the self-compaction question)
Summary (3) and kv-agent (6) use the same frontier compactor, so the representation is the only variable.

## Step 0: cache surgery correctness (before any results)
- An engine that keeps logical position ids separate from the physical cache index, with its own causal mask and length bookkeeping.
- Tests: (a) a no-op edit reproduces the untouched logits exactly; (b) a sparse cache matches explicit
  masked attention over the full cache; (c) the next logical position after pruning = L, not len(cache).
- Record queries during prefill (streaming top-k attention stats; never materialize 32k^2 matrices).

## Step 1: replay pilot
- Sessions: ~8 on-policy Qwen sessions (Qwen runs real repo tasks past 32k) as the primary set; ~20 Claude
  Code / Pi transcripts as a separate robustness set. Split into development and held-out sessions.
- Probes are frozen before any compaction: ~30 per session, generated by Claude, each tied to prefix evidence, labeled
  historical vs current-state; graded by a blind judge. Planted facts only in explicitly modified transcripts.
- Metrics: probe accuracy (primary); excess NLL versus full by distance after the cut (first decision weighted);
  compaction cost. Bootstrap over sessions.
- Gate: kv-agent > summary+tail AND > tuned-heuristic on held-out sessions.

## Step 2: live (only if the gate passes)
mini-swe-agent with Qwen, with tasks chosen so compaction actually fires (often repeatedly). Measure resolve rate,
repeated work and compaction exposure. Treat ~30 tasks as a pilot.

## Deferred
Merging, head-specific budgets, amortized policies or weight edits, Pi integration.

## Build: new Python repo `kvcompact` (uv)
engine/ (model, cache, positions, surgery, tests) · sessions/ (loaders, on-policy generator, probes) ·
methods/ (one file per method) · compactor/ (kernel tool loop, frontier + Qwen backends) · eval/ · runpod/

## Cost (to re-benchmark after one full loop)
H200 ~$3.5-4/hr; step 0 + pilot ≈ 1 week, ~$100-200 GPU + Claude compactor tokens.
